# DUP-010 — Fix report-layer `names_anywhere` math and clearly separate report baselines from collision-null baselines

**Priority:** P0  
**Status:** Completed (2026-02-28)  
**Depends on:** DUP-001

## Goal
Correct the mathematically incorrect expectation for distinct duplicated names in a bucket, and make it impossible to confuse:
1. report-layer proportional-share expectations,
2. detector-native collision expectations,
3. VRDB sidecar collision-null expectations.

## Problem
Distinct duplicated names in a bucket cannot be estimated by simple linear rescaling of a hearing-wide count. That ignores name multiplicities and creates misleading “expected” values.

## Scope
- Replace the current `names_anywhere` expectation with an occupancy-based expectation that respects multiplicities.
- Keep `rows_anywhere` only if it is explicitly labeled as a proportional-share baseline.
- Add visual and textual distinction among:
  - proportional-share baseline
  - detector collision baseline
  - VRDB collision baseline
- Reuse DUP-001 declaration plumbing (baseline label/source + inferential status + gating) so every affected chart/table keeps explicit baseline-family identity.

## Failure modes and mitigations
- **Failure mode:** users compare these three expectations as if they were interchangeable.  
  **Mitigation:** different labels, tooltips, and field names.
- **Failure mode:** dashboards display “expected duplicates” without naming which baseline generated them.  
  **Mitigation:** require baseline family and method label in every chart/table.

## Acceptance criteria
- `names_anywhere` expectation matches hand-checkable toy examples.
- Report labels clearly distinguish baseline types.
- No chart uses an unlabeled generic “expected duplicates” label.
- Updated charts/tables continue to show declaration notes that identify baseline family and inferential status.
