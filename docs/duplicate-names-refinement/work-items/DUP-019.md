# DUP-019 — Treat `unmatched_only` inference as descriptive-only until a dedicated unmatched baseline exists

**Priority:** P2  
**Status:** Planned

## Goal
Avoid spurious significance when the scope population is not represented by the baseline population.

## Problem
If a scope is explicitly “not matched to the voter registry,” then a voter-registry baseline is not a defensible inferential population for that scope.

## Scope
- For `unmatched_only` with registry-based baselines:
  - emit descriptive-only or unavailable status
  - suppress p/q/z and significance flags
- Add explicit report language explaining why
- Add future hook for a dedicated unmatched baseline if one is later developed

## Failure modes and mitigations
- **Failure mode:** unmatched-only appears extremely anomalous simply because the baseline excludes the relevant population.  
  **Mitigation:** disable inference until a proper baseline exists.
- **Failure mode:** analysts mistake descriptive-only summaries for inferential calls.  
  **Mitigation:** same descriptive-only badge/rules as DUP-008.

## Acceptance criteria
- No inferential outputs are produced for unmatched-only under registry baselines.
- Reports clearly state why unmatched-only is descriptive-only.
- Future dedicated-baseline extension path is documented.

## Verification
- Unit tests for unmatched-only mode guards.
- UI snapshot tests for descriptive-only labeling.
- Regression tests ensuring p-values stay suppressed.
