# DUP-005 — Integrate VRDB collision metrics as a sidecar evidence family, not a replacement

**Priority:** P0  
**Status:** Done (2026-02-28)  
**Depends on:** DUP-004

## Goal
Add VRDB collision evidence to the report and pipeline without overwriting or reinterpreting existing evidence families.

## Scope
Create a new additive output namespace and table, for example:
- `vrdb_collision_evidence`

Suggested fields:
- `slice_id`
- `slice_type`
- `N`
- `baseline_variant`
- `effective_geo_level`
- `observed_pairs`
- `expected_pairs_mean`
- `expected_pairs_p95`
- `expected_pairs_p99`
- `tail_prob_pairs`
- `observed_max_name_count`
- `expected_max_name_count_mean`
- `tail_prob_max_name`
- `top_overrun_names`
- `normalization_version`
- `vrdb_version`

## Explicit non-goals for v1
- No composite “super-score”
- No threshold changes to existing analyses
- No overwriting of existing columns
- No replacement of registry-similarity, timing, metadata, or content analyses

## Failure modes and mitigations
- **Failure mode:** VRDB metrics quietly become the “main” explanation in reports.  
  **Mitigation:** separate namespace, separate report section, and no merged score in v1.
- **Failure mode:** existing dashboards start reading VRDB tables as if they were old detector tables.  
  **Mitigation:** additive join only; existing schemas remain unchanged.
- **Failure mode:** analysts assume a null disagreement means one family is “wrong.”  
  **Mitigation:** see DUP-006; disagreement must be surfaced, not collapsed.

## Acceptance criteria
- Existing analyses run unchanged.
- VRDB metrics appear as new outputs only.
- Existing thresholds, column names, and detector contracts remain unchanged.
- Reports show VRDB metrics alongside other evidence families, not instead of them.

## Verification
- Contract tests confirming zero breaking changes to existing outputs.
- Integration tests joining the new table into the report payload.
- Snapshot tests for the new report section.
