# DUP-007 — Backtest the VRDB collision module before operational rollout

**Priority:** P0  
**Status:** Planned  
**Depends on:** DUP-004, DUP-005

## Goal
Demonstrate that the new VRDB collision evidence is stable enough to inform public reporting and official follow-up, without pretending the VRDB null is perfect.

## Scope
Validate on three data families:
1. normal historical hearings
2. known or suspected problematic hearings
3. synthetic hearings drawn from the VRDB null and controlled perturbation scenarios

Required comparisons:
- statewide vs county-conditioned vs city-conditioned baselines
- denominator variants if active-only vs broader registry universes are available
- normalization-version sensitivity
- small-bucket behavior
- city/geography quality issues
- tail behavior for expected pairs and max repeat count

## Rollout rule
The module does not ship operationally until this memo exists and is reviewed.

## Failure modes and mitigations
- **Failure mode:** tuning and evaluation use the same hearings.  
  **Mitigation:** separate calibration set from holdout validation set.
- **Failure mode:** validation over-focuses on suspected bad hearings and ignores false positives.  
  **Mitigation:** require a normal-controls section in the memo.
- **Failure mode:** synthetic checks are too easy.  
  **Mitigation:** include edge cases with sparse buckets, noisy geography, and homonym-heavy legitimate samples.

## Acceptance criteria
- Historical controls show acceptable false-positive behavior for a screening tool.
- Sensitivity to baseline variant and normalization choice is measured and documented.
- The memo states where the signal is stable and where it should be treated cautiously.

## Verification
- Reproducible backtest pipeline with fixed seed support.
- Written memo checked into repo or release artifacts.
- Review sign-off before report rollout.
