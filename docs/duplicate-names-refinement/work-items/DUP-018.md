# DUP-018 — Enforce one primary inferential key; keep nickname-based views as sensitivity analyses only

**Priority:** P2  
**Status:** Planned

## Goal
Ensure that inferential outputs, timing views, and report filters are not silently talking about different entity definitions.

## Scope
- Choose one primary inferential key for collision inference.
- Recommended default: strict full-name key.
- Keep nickname-based grouping as a sensitivity view only.
- Align timing and report displays to the active inferential key by default.

## Constraints
- No phonetic matching.
- No spelling correction.
- Nickname-table expansion is allowed.
- Other fuzzy matching is out of scope.

## Failure modes and mitigations
- **Failure mode:** users compare a strict inferential result to a nickname-based timing table and assume they refer to the same grouping.  
  **Mitigation:** sensitivity badges and explicit key labels in all tables.
- **Failure mode:** engineers add new loose modes that exceed project policy.  
  **Mitigation:** config guardrails and tests.

## Acceptance criteria
- Every inferential result states which key generated it.
- Sensitivity views are clearly separated from primary inference.
- No hidden key-mode switching occurs in the UI.

## Verification
- Payload tests for consistent key labeling.
- UI tests for sensitivity badges.
- Regression tests blocking unauthorized fuzzy matching modes.
