# DUP-011 — Define hypothesis families, gating, and multiplicity control across the detector

**Priority:** P1  
**Status:** Planned

## Goal
Prevent dashboard-wide false positives by ensuring every inferential result belongs to an explicit hypothesis family with a stated correction rule.

## Scope
Define families such as:
- Family A: scope-level collision tests
- Family B: per-name tests
- Family C: bucket follow-ups
- Family D: within-name follow-ups (temporal, position)

Recommended hierarchy:
- run Family B/C only if Family A passes for that scope
- run Family D only for names that pass Family B

Store, at minimum:
- `family_id`
- `adjustment_method`
- `n_tests`
- `eligible_by_gate`
- `gate_reason`

## Failure modes and mitigations
- **Failure mode:** users infer significance by browsing many unadjusted outputs.  
  **Mitigation:** every inferential table must declare family and adjustment.
- **Failure mode:** downstream tables appear even when upstream evidence is absent.  
  **Mitigation:** enforce gating in the backend, not just the UI.

## Acceptance criteria
- Every inferential p-value belongs to exactly one family.
- Downstream families are gated by upstream results.
- Reports show test counts and correction method.

## Verification
- Unit tests for family construction and BH/BY logic.
- Integration tests for gating behavior.
- Snapshot tests for family metadata in reports.
